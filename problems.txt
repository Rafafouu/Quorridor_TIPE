pourquoi nos bots décident de faire des allez retours plutot que de gagner

Le problème vient probablement de la combinaison de :

    une fonction d’évaluation trop “locale”

    une profondeur de recherche trop faible

    l’absence de mémoire des positions répétées

Du coup l’alpha-beta trouve plusieurs coups avec quasiment la même valeur et peut préférer des allers-retours.

Dans ton code, le principal suspect est ici dans eval_a_star et variantes :

Tu évalues seulement :

    longueur de TON chemin

    longueur du chemin adverse

    nombre de barrières

Mais tu ne récompenses jamais explicitement :

    le progrès réel vers la victoire,

    le fait d’éviter les répétitions,

    ou le fait de finir rapidement.

Donc un bot peut voir :

    avancer → score = 3.0

    reculer → score = 3.0 aussi

et comme alpha-beta prend le premier meilleur coup trouvé, il oscille.

Autre point très important :

Dans a_star_shortest_physical_path() tu ignores complètement la position réelle de l’autre joueur :

Tu le notes toi-même :

# NE PREND PAS EN COMPTE L'AUTRE JOUEUR

Donc l’évaluation croit parfois qu’un chemin est “équivalent” alors qu’en pratique un mouvement rapproche d’un saut ou d’un blocage stratégique.

Le vrai bug comportemental est souvent là :

return -1.5*len(j_path) + len(other_path)

Si :

    avancer réduit ton chemin de 1

    mais permet à l’adversaire de réduire aussi son chemin de 1

alors le score peut rester identique.

Résultat :

    le moteur “n’a pas de préférence”

    il tourne.

Tu peux corriger ça avec plusieurs techniques.
1. Bonus de progression (le plus important)

Ajoute une récompense pour avancer réellement vers la ligne d’arrivée.

Par exemple :

progress = joueur.case.row

ou inverse selon le joueur.

Puis :

return (
    -1.5 * len(j_path)
    + len(other_path)
    + 0.3 * progress
)

Ça casse immédiatement les allers-retours.
2. Pénalité de répétition

Très efficace.

Tu gardes les dernières positions :

self.previous_cases = deque(maxlen=6)

et dans l’éval :

if joueur.case in joueur.previous_cases:
    score -= 2

Les moteurs d’échecs utilisent ce genre d’idée.
3. Bonus de victoire rapide

Tu le fais déjà un peu :

1000000000 + profondeur

Ça c’est bien :

    gagner plus tôt est préféré,

    perdre plus tard aussi.

Mais ce bonus n’aide PAS dans les positions non terminales.
4. Augmenter la profondeur

À faible profondeur :

    le bot voit “avance”

    puis “l’adversaire répond”

    mais ne voit pas la suite gagnante.

Donc il stagne.

C’est extrêmement fréquent dans les minimax.
5. Ordonner les coups

Actuellement :

liste_actions = plateau.get_all_legal_actions(current)

mais elles ne sont pas triées.

Donc l’alpha-beta peut choisir arbitrairement un move neutre avant le bon.

Trie les coups :

moves_first = sorted(
    liste_actions,
    key=lambda a: a.type != "MOVE"
)

ou mieux :

    mouvements qui réduisent la distance d’abord,

    murs ensuite.

6. Le plus gros problème théorique : horizon effect

Ton bot peut faire :

    avance

    recule

    avance

    recule

car la conséquence négative est au-delà de la profondeur explorée.

C’est le “horizon effect”.

Solution :

    profondeur plus grande,

    quiescence search,

    ou heuristique plus agressive sur le progrès.

La correction la plus rentable immédiatement :

def eval_a_star(joueur):

    other = joueur.plateau.get_other_player(joueur)

    j_path = joueur.a_star_shortest_physical_path()
    other_path = other.a_star_shortest_physical_path()

    progress_bonus = (
        joueur.case.row
        if joueur.goal[0].row > joueur.case.row
        else -joueur.case.row
    )

    return (
        -2 * len(j_path)
        + 1.2 * len(other_path)
        + 0.5 * progress_bonus
    )

et surtout :

score -= repetition_penalty

C’est généralement ça qui élimine les “bots qui dansent”.
